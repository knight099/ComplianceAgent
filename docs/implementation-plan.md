## Enterprise access and privacy delivery sequence

The first release should answer one question end to end. When an employee transfers out of Lending, does an old approval or group still give them read access to restricted KYC data? Keep the read-only pilot usable at every milestone. These are proposed deliverables. Live connector qualification depends on customer-authorized credentials, representative test accounts and access to the relevant product APIs.

### Which source answers which question?

| Question | First source | Expansion |
|---|---|---|
| Who is the employee, and what business role do they hold now? | Current HR export and exact Entra employee-ID match | Darwinbox or Workday for dated employment changes |
| What should the employee be able to read? | Data owner's versioned classification, role policy and exceptions | Data catalog for resource labels and ownership |
| What access was requested, approved or certified? | Planned read-only Saviynt connector for accounts, entitlements, assignments and available approval, expiry and certification evidence | SailPoint for governance records, Jira or ServiceNow for supporting approvals |
| What access can the account exercise? | PostgreSQL catalog grants and role paths | Entra and Okta group assignments, AWS IAM and S3 policies, GitHub organization, team and repository permissions |

Preserve discrepancies. An approved Saviynt request explains how access was authorized at a point in time. An expired approval, a current business-role mismatch and a PostgreSQL grant can all coexist. Retain source identifiers, timestamps, coverage and tenant scope on each fact. A missing page, ambiguous account or inaccessible target leaves the relevant question open.

### Personal data before any LLM call

The authenticated summary route reads three counts, the collection time and freshness. At the outbound boundary, the model client accepts only the approved aggregate shape, omits the timestamp and bands each count. The connection test sends a fixed prompt. Both operations use server-approved models and provider destinations. The following requirements also govern any future expansion to text or tools.

- Build outbound payloads from a typed allowlist for each operation. Omit names, emails, employee and account IDs, customer rows, Aadhaar and PAN values, raw evidence and credentials from model content. Keep provider authentication secrets confined to the transport credential. Allow tenants to disable inference or restrict destinations.
- Where an approved investigation needs to follow the same subject across evidence, issue an opaque case- and tenant-scoped alias. Keep the mapping inside the tenant boundary. Treat pseudonymized evidence as sensitive. Apply separate rules for small counts or unusually identifying combinations.
- Screen approved text locally before transmission. Block unrecognized fields, unsafe free text, masking failures and unapproved destinations. Apply the same rules to retrieved passages, tool outputs, retries, tracing and logs. Record the policy version and decision without storing the raw prompt.
- Seed synthetic identifiers and secrets into nested fields and retrieved text. Inspect outbound model bodies, logs and traces. Assert that forbidden values never appear, aliases cannot correlate tenants, and a rejected payload produces zero provider calls. Run these tests for external and private endpoints.
